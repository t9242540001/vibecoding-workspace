### ФАЗА 2 — T3-research: выбор поискового движка

**Это самостоятельная T3-задача.** Не серия промптов, а исследование с premortem, командой специалистов и письменным ADR в decisions.md.

**Активация:** skill `research-protocol` полностью, 4 фазы (Frame → Investigate → Critique → Decide).

**Вопрос исследования:**
> Какой веб-поисковый движок использовать для Sub-Research Agent в MVP-стадии Products Research Agency, и при каких условиях этот выбор пересматривать?

**Кандидаты для рассмотрения** (минимум, можно расширять):
- Tavily Search API (заточен под AI agents, $30/мес за 1000 поисков)
- Serper.dev (Google search proxy, ~$50 за 50K)
- Brave Search API (~$3 за 1K)
- SerpAPI (Google/Bing/Yandex aggregate, дорогой)
- Свой парсинг (бесплатно, риски блокировок, нагрузка)
- Яндекс XML Search (для RU-сегмента — особенно важно для тендерного контекста)
- Sequential combination (например: Brave для широты + Tavily для точности)

**Команда виртуальных специалистов** (минимум 3, использовать ростер из STANDARDS § 1.6):
- Архитектор — интеграция с LangGraph, retry/fallback semantics, скорость отклика
- Финансовый аналитик — стоимость на месяц для разных тиражей (10/50/200 отчётов)
- Юрист-аналитик — комплаенс по 152-ФЗ и санкции (US-сервисы из РФ могут быть проблемны)
- Маркетолог-growth — качество для русскоязычных тендерных запросов конкретно
- Безопасность — TLS, утечки query содержимого через прокси, IP-fingerprinting от сервиса

**Обязательные критерии оценки** (premortem):
- Что будет если Tavily/Serper резко перестанут отдавать ответы из РФ? (санкции, IP-блок)
- Что будет если стоимость выйдет за $100/мес на стадии 50 отчётов?
- Что будет если качество для RU-тендерных запросов окажется значимо хуже англоязычных?
- Что будет если правовые требования по ПДн запретят отправлять извлечённые из ТЗ строки в US-сервис?

**Что должно получиться на выходе:**
1. Письменный ADR в `knowledge/decisions.md § Active Iterations` с заголовком `### 2026-05-11 — Web search engine for Sub-Research Agent`. Формат как другие Active Iterations: контекст, варианты, выбор, обоснование, триггеры пересмотра.
2. Краткий план интеграции (какие env vars нужны, какой код в `src/llm/` или новом `src/search/`)
3. Стоимостная модель: $/месяц при 10, 50, 200 отчётах
4. Risk map: что мониторим, какие fallback'и заложены архитектурно

**Это БОЛЬШАЯ серия промптов** (~12–18 штук, точное число зависит от декомпозиции, которую сделает новый Claude).

**Предварительные шаги перед началом написания промптов:**

1. **Прочитать заново** (актуальное состояние после Фазы 1):
   - `knowledge/agents-spec.md` — точные IO schemas для каждого агента
   - `knowledge/multiagent.md § Verification Cycles` — где валидаторы из Фазы Batch A включаются
   - `knowledge/decisions.md` — новый ADR по поисковому движку из Фазы 2

2. **Парад промптов перед запуском batch'а обязателен.** Без одобренного парада серия не запускается. См. `batch-execution-standard.md § 4`.

3. **Триаж сложности по каждому агенту индивидуально.** Не все одинаковые:
   - Intake Agent — простейший (T1 в рамках T3-серии: один LLM-вызов на классификацию)
   - Lead Agent — простой (T1: декомпозиция через один LLM-вызов)
   - **Sub-Research Agent — самый сложный** (T2-T3: интеграция с поисковым движком + LLM на извлечение фактов; может потребовать 2–3 промпта)

   - Verifier — средний (T2: уже использует numeric validators из Фазы Batch A)
   - Writer — средний (T2: один LLM-вызов с большим промптом)
   - Judge / Reviser — средние (T2: каждый один LLM-вызов с конкретным форматом ответа)

4. **Mock LLM pattern для тестов.** Все тесты Batch C должны мокать LLM (не делать реальные вызовы) — это требование `knowledge/testing-strategy.md § Integration tests`. Реальный e2e прогон один раз в конце Batch C (~$1–2 на DeepSeek).

**Что НЕ делает Batch C** (важно для REGRESSION SHIELD каждого промпта):
- Не поднимает VDS (это Batch B, после Batch C)
- Не меняет structure агентов в graph.py (только тела `run()` функций)
- Не меняет IO schemas (они зафиксированы в Batch A; если по ходу окажется что схема неудачна — STOP и в чат)
- Не добавляет новых агентов (9 → 9, без расширения)
- Не трогает `src/validators/numeric.py` (готов, используется Verifier'ом as-is)
- Не трогает `src/docx/` (готов)

**Failure recovery:**
- `stop_on_failure: true` обязателен
- Каждый агент-промпт независимо проверяемый (тесты на конкретный агент проходят)
- При падении одного — откат через `git revert` соответствующего commit, fix, ретриггер с того же `batch_id`
